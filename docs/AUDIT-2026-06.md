## 1. Where & how documents are stored

**Two halves: the file blob lives in Supabase Storage, the metadata lives in Postgres.**

| Concern | Where | Detail |
|---|---|---|
| File bytes | Supabase **Storage** bucket `documents` | Private bucket (`public: false`), 10 MB limit, mime allow-list (pdf, text/*, image/*, Word). Created on demand by [`/api/storage/setup`](../pages/api/storage/setup.ts). |
| Object path | inside the bucket | `documents/<timestamp>_<filename>` — set in [`pages/content/index.tsx`](../pages/content/index.tsx). |
| Metadata record | Postgres table **`content`** | One row per upload: `title`, `type` (general/cv/certificate/reference), and a `metadata` JSONB blob holding `path`, `bucket`, `size`, `uploadedAt`, `version` (for CV history), AI `summary`/`talkingPoints`/`keywords`, and `shareLinks[]`. |
| AI summary | [`/api/documents/summarize`](../pages/api/documents/summarize.ts) | The client reads the first ~4 000 chars of the file text and sends it to the free GitHub Models endpoint; the returned summary/keywords are saved into the `content.metadata`. |
| Sharing | Supabase signed URLs | "Share" creates a time-limited `createSignedUrl` (1 h / 24 h / 7 d) and appends it to `metadata.shareLinks`. |

**Security posture:** the bucket is private and per-user isolation is enforced by
RLS on the `content` table — the file path is only discoverable through your own
`content` rows. Sharing is explicit and expiring.

**Bug fixed in this pass:** the "Open" button generated a link with
`getPublicUrl()`, which **does not work on a private bucket** (it returns an
unsigned URL the storage API rejects). Replaced with a short-lived
`createSignedUrl(path, 300)`. See [`pages/content/index.tsx`](../pages/content/index.tsx).

## 2. 🔴 Critical finding: inserts fail RLS because `user_id` has no default

**Symptom:** creating a goal (and, by the same mechanism, tasks, notes, body
stats, finance entries, motivations, etc.) silently fails — the row never
persists.

**Root cause:** `schema.sql` declares `user_id uuid ... not null` with **no
default** on almost every table, while the RLS insert policies require
`auth.uid() = user_id`. The client hooks insert rows **without** a `user_id`,
so every insert is rejected (`42501 violates row-level security policy`). Only
`body_workouts` had `default auth.uid()` and therefore worked.

**Fix (two layers):**
1. **Systemic** — [`supabase/fix-user-id-defaults.sql`](../supabase/fix-user-id-defaults.sql)
   adds `default auth.uid()` to `user_id` on every user-owned table. **Run this
   in the Supabase SQL editor** (after `schema.sql` + `security-and-performance.sql`).
   This makes all existing client inserts correct.
2. **Defensive** — the goals hook now also sets `user_id` explicitly on insert,
   so goal creation works even before the migration is applied.

> **Applied 2026-06-22** via the Supabase MCP — all 24 `user_id` columns now
> default to `auth.uid()` (verified: 0 missing). `fix-user-id-defaults.sql` is
> the reproducible record (dynamic — covers every table with a `user_id`).

### Follow-on: two RLS holes found by the security advisor

After the DDL change, Supabase's security advisor flagged **2 ERROR-level**
issues: `habits` and `habit_logs` had **RLS disabled** (added after the original
security migration, so never covered) — either account could read/write the
other's habits. **Fixed + applied 2026-06-22** ([`supabase/enable-rls-habits.sql`](../supabase/enable-rls-habits.sql)).
Advisor re-run: **0 ERROR-level issues remain**. Remaining items are WARN-level
(pg_graphql discoverability, mutable function search_path, optional leaked-password
protection) — low risk for a 2-user app, listed as future hardening.

## 4. Fitness section overhaul

Researched how leading apps (Hevy, Strong, Fitbod, Caliber) present training and
added the patterns that matter most for a 2-person personal app:

- **Interactive anatomical muscle map** — [`components/MuscleMap.tsx`](../components/MuscleMap.tsx):
  front + back figures, 15 muscle groups, theme-aware, hover/tap for detail.
- **Exercise → muscle intelligence** — [`lib/muscles.ts`](../lib/muscles.ts):
  every logged set is mapped to the primary/secondary muscles it trains
  (keyword matcher covering the common barbell/dumbbell/bodyweight movements).
- **Recovery model** — each muscle is colored by readiness (green recovered /
  yellow recovering / red worked / grey untrained) based on time since last
  trained vs a per-muscle recovery window.
- **Coverage guidance** — weekly effective-set count per muscle vs a target,
  surfacing the biggest gaps ("train next").

Verified end to end: logging Bench/Curl/Squat correctly lit chest, front delts,
triceps, biceps, forearms, quads, glutes, and hamstrings.

## 5. AI-owned, date-aware goal setting

The AI is now the primary goal-setting engine.

- **[`/api/goals/plan`](../pages/api/goals/plan.ts)** — given an optional intent
  + your existing goals + **today's date**, it either proposes 1–3 SMART goals
  (each with a realistic future `target_date` and dated milestones) **or**, if a
  new goal isn't warranted, returns concrete recommendations instead. A
  server-side guard drops any non-future date the model emits.
- **Date awareness everywhere** — the existing goal coach now receives today's
  date and days-remaining, so momentum/risk reflect time pressure.
- **One-click adoption** — proposed goals (with milestones) are created in a
  single action from the Goals page.

Verified: with today = 2026-06-21 the planner produced goals at 1-month,
3-month, 6-month, and end-of-year horizons — all future, milestones ordered
before each target.

## 6. Recommended next features

Prioritized for a 2-user personal app (not SaaS scale):

**High value / low effort**
1. **Run `fix-user-id-defaults.sql`** (unblocks all create flows) — do this first.
2. **Household / shared mode** — opt-in sharing of goals, finance, and calendar
   between the two of you (currently every row is strictly per-user). This is a
   product decision: shared tables vs. a "partner can view" RLS policy.
3. **Exercise library + autocomplete** in the gym log, feeding the muscle map
   (removes free-text typos that break muscle attribution).
4. **Document text extraction for PDFs** — today only the raw text is read
   client-side; PDFs summarize poorly. Add pdf.js text extraction before summary.

**Medium**
5. **AI weekly review** — a Sunday digest across goals, training, mood, finance
   (the data and AI client already exist; just needs a scheduled compose step).
6. **Push/email reminders** for overdue goals & milestones (date-aware engine is
   now in place).
7. **Progressive-overload suggestions** in the gym (next-session targets from PR
   history).
8. **Calendar two-way sync** for goal milestones (create events from due dates).

**Larger / infra**
9. **Error tracking (Sentry)** — needs a DSN you create; wire into `ErrorBoundary`.
10. **Durable rate limiting** — current limiter is in-memory/per-instance; move
    to Supabase or Upstash if you ever go beyond personal scale.
11. **Burn down the ~29 `react-hooks/*` warnings** (React Compiler rules) when
    convenient — currently downgraded to warnings, not blocking.
